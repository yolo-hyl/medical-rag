# 方案

> 本文是项目的宏观方案：要解决什么问题、系统框架、解决思路、产品方向、需要什么数据，以及目前已确定和待讨论的方向。
> 技术结构、接口、存储和用法见 [architecture.md](architecture.md)。
> 开发阶段的划分（顺序、节点、验收标准）还没有确定，会另行讨论，本文不涉及。

## 1. 定位

**医学知识的可验证层。** 把医学知识文本变成带条件、带有效期、带出处的陈述（Claim），并在此之上回答问题：

- 按"时间点 + 适用条件"作答；
- 缺关键条件时先追问；
- 有分歧时如实呈现；
- 每一句都能核查到原文和版本。

项目的脉络分三步，后一步建立在前一步的成果之上：

| 方向 | 要证明或交付什么 | 形态 |
| --- | --- | --- |
| 论文（引子） | 在条件依赖、版本更新、来源分歧三类问题上，Claim 化的知识层明显优于文本块 RAG 和 LightRAG | 最小实现 + 中文时间切片评测集 |
| 开源库 | 知识层可以复用、可以增量维护，并且越用越干净 | 共享的内核 + 医疗领域包，即 `medrag` 包 |
| 产品 | 医生助手、患者助手 | 搭在内核和领域包之上的应用 |

内核只提供"事实"和"风险信号"，不替上层做决定。同一条"eGFR 30–45 不推荐起始二甲双胍"：
- 医生助手：直接给出阈值、原文和版本；
- 患者助手：提示需要先测肾功能、请医生判断，不给剂量建议。

## 2. 要解决的问题

医学知识有三个特性，现有 RAG（包括 LightRAG 这类 GraphRAG）默认它们不存在：

| 特性 | 例子 | 现有 RAG 的默认假设 | 后果 |
| --- | --- | --- | --- |
| 有条件 | 二甲双胍：eGFR < 30 禁用，eGFR 30–45 不推荐起始用药 | 知识无条件 | 给出平均答案；条件在摘要中丢失 |
| 会过期 | 二甲双胍说明书 2016 年起改为按 eGFR 而不是血肌酐判断禁忌；新冠诊疗方案三年出了十版 | 知识永久有效 | 新旧知识混在一起，引用到过时的内容 |
| 有分歧 | 高血压诊断阈值：2022 年《中国高血压临床实践指南》为 130/80 mmHg，《中国高血压防治指南》为 140/90 mmHg | 只有一个答案 | 分歧被抹平，或者只剩一边 |

展开成具体问题：

| 问题 | 例子 |
| --- | --- |
| 实体碎片与误合并 | "急性心肌梗死 / 心梗 / AMI"成了三个节点；"二甲双胍"和"盐酸二甲双胍缓释片"却被合成一个 |
| 没有医学 schema，不锚定标准术语 | 同一个意思抽出"治疗 / 用于 / 可治"三种关系；实体挂不上 ICD-10、ATC 编码 |
| 断言丢失 | "ACEI 类药物妊娠期禁用"被抽成 (ACEI, 相关, 妊娠) |
| 冲突被抹平 | 见上表"有分歧" |
| 时效与版本 | 见上表"会过期" |
| 溯源只到文档级 | 说不清"eGFR < 30 禁用"出自哪份文件的哪一句；实体描述是 LLM 摘要过的二手知识 |
| 安全与越权 | 让 LLM 自己算儿童剂量；胸痛伴大汗的用户只得到"注意休息" |
| 不做条件匹配 | 能不能吃二甲双胍取决于 eGFR，向量检索不会追问这个条件 |
| 评测只看准确率 | 选择题答对了，长答案里却夹着一句致命错误 |

LightRAG 的做法是：实体按名字合并，同一实体的多条描述交给 LLM 摘要；关系无向，也没有谓词类型；没有断言、有效期和冲突的概念；引用只到文档级。前六个问题它基本覆盖不到，后三个不在它的范围内。

## 3. 系统框架：三层

```
应用层     医生助手 · 患者助手 · 安全策略                        领域相关
领域包     医疗：schema · 术语 · 抽取规则 · 优先级与冲突规则 ·      领域相关，注入内核
          条件判定 · 确定性工具 · 风险规则 · 提示词
内核       Claim 模型 · 两条时间轴 · 冲突集 · 治理事件 · 三类存储 ·   领域无关
          检索与条件匹配 · 逐句核查 · 审计 · 评测框架
```

- **为什么要有领域包这一层**：领域适配有两类。查询时的适配（如何呈现、如何追问、安全策略）放在应用层；入库时的适配（有哪些实体和谓词、用什么术语、哪些章节要抽 Claim、冲突怎么判定）应用层够不着，只能以领域包的形式注入内核。
- **为什么内核要领域无关**：保留以后迁移到其他知识密集领域的可能。"带条件、有效期、出处的陈述 + 冲突分型 + 按优先级处理"这套骨架是通用的，变的只是每个领域的具体内容。
- **防止过度设计**：
  - 定位仍然是医疗，论文和产品都只做医疗；
  - 领域包的扩展点以医疗实际用到的为准，没有实际内容的扩展点一律不加；
  - 不为其他领域做任何预留。

## 4. 解决方案

### 4.1 知识表示：按风险分级 Claim 化

- **高风险知识抽成 Claim**，包括剂量、禁忌、相互作用、诊断阈值、控制目标、推荐意见。每条 Claim 包含：
  - 主体、谓词、客体；
  - 条件：人群、阈值、合并症、并用药；
  - 极性与模态（推荐强弱、绝对 / 相对禁忌）；
  - 有效期；
  - 原文出处，精确到句子和文档版本。
- **解释性文本**（机制、概述）保持文本块检索。这样成本可控，精力花在真正需要可验证的地方。
- **只处理知识文本**：指南、说明书、教材、政府文件、文献、医学问答，不处理病历、问诊对话这类患者文本。查询里的患者信息（如"我 eGFR 40"）由查询理解抽成条件。
- **断言与生俱来**：条件和极性在抽取时一次产出，不事后补。

### 4.2 两条时间轴

| 时间轴 | 含义 |
| --- | --- |
| 现实有效期 | 这条知识在现实中何时有效 |
| 系统时间 | 系统何时得知、何时撤回 |

- 默认按"现在有效"的知识回答；也能回答"截至某年的标准是什么"；审计时可以还原任意时刻的知识状态。
- 文档有版本链，分三种情况：
  - **更正**（如 OCR 纠错）：覆盖原版本；
  - **修订**（新版说明书、新版指南）：保留旧版并标记被取代；
  - **不同机构的指南**：不是取代关系，而是并存。

### 4.3 冲突：分型、保留、按类型处理

业内的共识是冲突不消除，而是分型、保留、按规则排序、透明呈现。在 CONFLICTS 基准的 5 类基础上扩展为 7 类，其中"权威度不同"在医疗里就是证据等级不同：

| 类型 | 例子 | 处理 |
| --- | --- | --- |
| 互补 | 两份资料各说了不同的不良反应 | 合并呈现 |
| 条件不同（伪冲突） | 成人剂量与儿童剂量 | 补全条件后冲突消失，查询时按条件过滤 |
| 时效 | 说明书新旧版本 | 新版本优先，旧版本标为过时并写上失效日期 |
| 学术分歧 | 高血压诊断阈值 130/80 与 140/90 | 不裁决，两边都呈现，附发布机构和证据等级 |
| 权威度不同 | 病例报告与 RCT 结论相反 | 按证据等级排序，低等级的作为补充 |
| 错误信息 | 低可信来源的说法 | 降权，进审核队列 |
| 抽取错误 | 系统自己漏抽条件造成的假冲突 | 回到原文复核，修正 Claim |

冲突在**入库时**检测并存下来，不在每次查询时临时交给 LLM 判断。有研究发现，仅仅调换两篇文档的顺序，就会改变 11%～25% 的判断。冲突的分型和检测由内核负责；每一类怎么处理由领域包的规则决定。

### 4.4 概念：规范化 + 可回滚的合并

- **锚定标准术语**：药物对应医保药品编码 / ATC，疾病对应 ICD-10，检验对应 LOINC。允许暂时锚定不了的概念存在，但要标出来。
- **粒度不同的不合并**，而是用关系连起来：成分—制剂—品牌、药物—类别、疾病—亚型。哪些关系可以把 Claim 向下继承（"ACEI 类妊娠禁用"适用于依那普利），由领域包声明。
- **合并可回滚**：每次合并都记成治理事件。查询时先只读地把候选碎片一起查上，回答之后由后台判定是否真的合并，也就是查询驱动的治理。

### 4.5 回答：先对齐条件，再作答

- **双通道检索**：Claim 和文本块同时检索，并沿概念层级扩展。
- **条件匹配**：用户条件和 Claim 条件做结构化比较，结果分为满足、不满足、缺失三种；缺少关键条件时返回追问。
- **逐句引用和核查**：每句标注引用，回答之后逐句核查。Claim 库没覆盖的部分用文本块作答，并标注"未结构化证据"。
- **回答路径只读**：查询不写知识库。查询中发现的碎片、未覆盖的文本、可疑的冲突，投进后台队列处理。

### 4.6 存储：关系库为唯一真相源

- **逻辑上**是超关系知识图谱，即陈述加限定信息，与 Wikidata 的"陈述 + 限定词"同类；**物理上**存在关系库（PostgreSQL / SQLite）里。
- **向量索引**（Milvus / Milvus Lite）负责"找到"：文本块、Claim 的文本化表述、概念别名。
- **图数据库**（Neo4j / FalkorDBLite）一开始就用。它是由治理事件驱动的投影，承担概念层级扩展、多跳查询（多药合用的相互作用、合并症）、解释路径和审核时的可视化。
- 向量和图都可以从关系库重建。

原则是"**向量负责找到，结构负责判断**"。医学里最致命的否定、阈值、人群，恰恰是向量最不擅长的：在 NevIR 上，除了交叉编码器略高于随机，其他检索模型都不如随机。

Claim 在入库时离线构建，查询时只查不建。StructRAG、LazyGraphRAG 那样在查询时构建结构，在医疗场景有四个硬伤：不可复现、冲突只能临时判断、没有审核机会、延迟高。

### 4.7 守护：内核给信号，应用层定策略

- **内核**：逐句核查、风险信号（缺失条件、引用了过时知识、属于高风险内容）、审计记录。
- **领域包**：确定性工具（剂量与肾功能调整、相互作用核对，查询结构化的 Claim，不让 LLM 计算），以及风险规则（哪些谓词是高风险的、红旗症状有哪些）。
- **应用层**：越权识别（诊断、处方类请求）、急症红旗的响应、PHI 脱敏、风险分级（直接返回 / 附提示 / 拦截或转人工），按受众配置。
- **合规**：《互联网诊疗监管细则（试行）》规定，人工智能软件不得冒用、替代医师本人提供诊疗服务；面向患者时不给诊断和处方。

### 4.8 评测：时间切片

- **流程**：文档按发布时间顺序分批入库，在每个时间点提问，以"当时有效"的答案为标准。这能直接暴露"增量入库时新旧描述被摘要到一起"的问题。
- **同时考察**：条件类（是否追问、是否按条件作答）、分歧类（是否呈现双方）、错误信息类（是否排除），以及 claim 级忠实度与安全关键错误率。
- **对比**：
  - 基线：不检索、文本块混合检索、LightRAG；
  - 消融：去掉条件、去掉有效期、去掉图扩展、去掉冲突集。

## 5. 与相关工作的区别

| 工作 | 做法 | 与本项目的差异 |
| --- | --- | --- |
| LightRAG、Microsoft GraphRAG | 入库时抽实体和关系，描述由 LLM 摘要 | 没有条件、有效期、冲突；溯源只到文档 |
| HippoRAG | 相似实体之间加同义边 | 只解决连通性，不处理粒度和断言 |
| Graphiti（Zep） | 双时态边，新事实使旧边失效 | 时间维度上最接近，但面向通用的 Agent 记忆，用二元边，没有医学条件和证据等级 |
| StructRAG、LazyGraphRAG | 查询时临时把文档结构化 | 不可复现，冲突无法预先判定，没有审核环节 |
| Medical Graph RAG | 把实体链接到可信文献和 UMLS | 没有有效期和冲突处理；以英文为主 |
| KAG（OpenSPG） | schema 约束抽取、图与原文互索引、逻辑形式推理 | 不以时效和冲突为核心 |

## 6. 产品方向

### 6.1 论文（引子）

- **主张**：Claim 化 + 时效 / 条件 / 分歧，用时间切片评测来证明。
- **范围**：中文为主，纵向切片选**糖尿病、高血压、心血管一级预防**。先在窄领域把各层做薄、做通、测出效果，再往外扩，好让最大的风险——Claim 抽取的质量撑不起整套设计——尽早暴露。
- **最小实现需要的部分**：Claim 抽取（带条件和原文出处）、概念规范化与层级、版本与有效期、冲突分型、按条件检索并带引用作答、逐句核查。
- **评测**：时间切片评测集（300～500 题）、Claim 抽取金标准（约 300 条），基线与消融见 4.8。

### 6.2 开源库

- 共享的内核 + 医疗领域包。
- 查询驱动的后台治理：合并候选判定、未覆盖文本补抽 Claim、冲突复核、人工审核队列、按事件回滚。
- 英文支持：DailyMed 说明书的历史版本、FDA 药品安全通告、ADA Standards of Care 的年度修订摘要。一个 workspace 只放一种语言。
- 数据下载与校验工具、命令行、文档与示例；规模化（全量教材、更多切片）；在 GraphRAG-Bench medical 上对标 LightRAG。
- 现有的 SimpleRAG / DialogueRAG / MedicalAgent 改为调用内核的统一查询接口。
- 数据扩充：Huatuo 百科全量、MIRAGE、CMB-Clin（用于多轮问诊评测）。

### 6.3 产品

- **医生助手**：临床决策辅助，给出完整证据、版本和分歧。
- **患者助手**：健康咨询，回答保守、易读，做急症分诊。
- **守护**：扩充确定性工具，加上风险分级、PHI 脱敏、急症红旗、审计与合规。
- `software/` 前后端适配新接口。

| 标注 | Claim 金标准约 300 条；时间切片题 300～500 道，每道有"截至某日"的答案和出处版本；冲突类型 | 1～2 位医学背景的标注者 | 这是真正的瓶颈 |

**规范化与辅助评测**

| 数据 | 用途 | 获取渠道 |
| --- | --- | --- |
| 医保药品分类与代码（通用名、商品名、剂型、规格、批准文号、本位码） | 构建成分—制剂—品牌的层级 | 国家医保局的编码标准动态维护平台 |
| ICD-10 国家临床版 2.0、医保版 2.0 | 疾病规范化 | 卫健委、医保局下发的编码库 |
| ATC 分类 | 药物类别层级 | WHOCC（完整索引需购买）；台湾政府资料开放平台有开放授权的 ATC 数据集 |
| LOINC（含中文译文） | eGFR、HbA1c 等检验指标的规范化 | loinc.org 免费注册下载，中文译文不完整 |
| CBLUE（CMeIE、CHIP-CDN） | 评测抽取和规范化这两个子环节 | 天池注册下载 |
| CMB、MedQA 中与切片相关的题目 | 静态知识对照 | MedQA 已有；CMB 在 Hugging Face |

**英文（开源库方向）**

DailyMed / openFDA（说明书历史版本，可以按 set_id 逐版本下载）、FDA 药品安全通告、ADA Standards of Care 的年度修订摘要、USPSTF 推荐的更新记录、DriftMed、HealthContradict。

**分工**：公开的政府文件和公告用脚本抓取；指南全文、说明书全文（尤其是历史版本）、医保和 ICD 编码库、标注人力，由维护者想办法。

### 7.2 已有数据的用途

| 数据 | 用途 |
| --- | --- |
| huatuo QA（`data/qa_50000.jsonl`、`data/eval/new_qa_200.jsonl`） | 文本块通道的回归基准（Hit@k） |
| MedQA 中文教材与题库 | 解释性文本（内科学、药理学等）；选择题作为静态知识对照。教材的 OCR 错字很多，统一用 LLM 纠错：只改错字，不补内容，丢失的数字不补 |
| GraphRAG-Bench medical（英文） | 开源库方向上对标 LightRAG |

数据里其他已知的坑记录在 CLAUDE.md。

### 7.3 版权原则

- 期刊指南和商业说明书库只用于研究。评测集对外只发布标注、问题和出处，不分发原文。
- 政府文件可能适用《著作权法》第五条（行政性文件不受该法保护），公开发布前需要确认。

## 8. 风险

| 风险 | 应对 |
| --- | --- |
| Claim 抽取的质量撑不起整套设计 | 用金标准尽早量化；限定符分为"必须"和"以后再加" |
| 说明书历史版本拿不到 | 时效题以指南版本和政府文件为主，说明书只作为当前知识 |
| 标注人力不足 | 改成 LLM 预标注加专家抽检，论文里如实说明 |
| 版权 | 见 7.3 |
| 成本 | 只对高风险文本抽 Claim；离线一次性构建 |
| 过度设计 | 只做医疗；领域包只开医疗用得上的扩展点；查询驱动的治理放到开源库方向 |
| 图投影与关系库不一致 | 图只是派生索引，可以按事件重放重建；trace 里记录投影进度 |

## 9. 已确定的方向与待讨论的问题

**已确定**

- 定位是医学知识的可验证层；脉络是论文 → 开源库 → 产品，内核共享，上层搭医生助手和患者助手。
- 三层结构：领域无关的内核、医疗领域包、应用。只做医疗，领域包只开医疗用得上的扩展点。
- 包名暂时保持 `medrag`，领域包放在包内的 `domains/medical/`。
- 只处理知识文本，不处理病历、问诊对话等患者文本。
- Claim 节点化（n 元陈述是一等对象），按风险分级抽取，条件与极性在抽取时产出。
- 允许未锚定标准术语的概念存在，但必须标记。
- 关系库是唯一真相源；向量索引和图数据库是派生索引，都可以重建；图数据库一开始就用。
- 纵向切片：糖尿病、高血压、心血管一级预防；中文为首要开发语言，英文后续支持。
- 保留已实现的公共基础：中间件降级、只用异步、依赖注入、核心层与应用层的分层、OpenAI 兼容的模型层、版本化提示词。

**倾向（待确认）**

- Claim 在入库时离线构建；回答路径只读，写入只经由入库或后台治理。
- 论文主线：Claim 化 + 时效 / 条件 / 分歧 + 时间切片评测；查询驱动的治理作为开源库的特色，也可以作为第二篇论文。
- 安全策略放在应用层，按受众配置；内核只给事实和风险信号。

**待讨论**

- 开发阶段的划分：顺序、节点、验收标准。
- 标注人力从哪里来；找不到时是否采用 LLM 预标注加专家抽检。
- 说明书历史版本的获取渠道：商业库、药企、医院药剂科，三者中选哪条。
- 政府文件、期刊指南用于研究和发布评测集的版权边界。
- SNOMED CT 在中国是否可用、怎么授权；在此之前不依赖它。
- 医疗领域包的首版 schema：实体类型、谓词、条件变量、限定符清单，需要用金标准来定稿。
- 稀疏检索选 pkuseg 自管理词表还是 Milvus 原生 BM25（两者放在同一接口之后，用 A/B 实验来定）。
