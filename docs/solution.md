> 本文是项目的宏观方案：要解决什么问题、怎么解决、分几步走、需要什么数据，以及方向性决策的记录。

## 1. 定位

**医学知识的可验证层。** 把医学知识文本变成带条件、带有效期、带出处的陈述（Claim），并在此之上回答问题：

- 按"时间点 + 适用条件"作答；
- 缺关键条件时先追问；
- 有分歧时如实呈现；
- 每一句都能核查到原文和版本。

项目分三步走，后一步建立在前一步的成果之上：

| 阶段 | 要证明或交付什么 | 形态 |
| --- | --- | --- |
| 论文（引子） | 在条件依赖、版本更新、来源分歧三类问题上，Claim 化的知识层明显优于文本块 RAG 和 LightRAG | 最小实现 + 中文时间切片评测集 |
| 开源库 | 知识层可以复用、可以增量维护，并且越用越干净 | 共享的 core，即 `medrag` 包 |
| 产品 | 医生助手、患者助手 | core 之上的应用层智能体，各自配置安全策略 |

**core 和上层的分工**：core 只提供"事实"和"风险信号"，不替上层做决定。同一条"eGFR 30–45 不推荐起始二甲双胍"：
- 医生助手：直接给出阈值、原文和版本；
- 患者助手：提示需要先测肾功能、请医生判断，不给剂量建议。

## 2. 要解决的问题

医学知识有三个特性，而现有 RAG（包括 LightRAG 这类 GraphRAG）默认它们不存在：

| 特性 | 例子 | 现有 RAG 的默认假设 | 后果 |
| --- | --- | --- | --- |
| 有条件 | 二甲双胍：eGFR < 30 禁用，eGFR 30–45 不推荐起始用药 | 知识无条件 | 给出平均答案；条件在摘要中丢失 |
| 会过期 | 二甲双胍说明书 2016 年起改为按 eGFR 而不是血肌酐判断禁忌；新冠诊疗方案三年出了十版 | 知识永久有效 | 新旧知识混在一起，引用了过时的内容 |
| 有分歧 | 高血压诊断阈值：2022 年《中国高血压临床实践指南》为 130/80 mmHg，《中国高血压防治指南》为 140/90 mmHg | 只有一个答案 | 分歧被抹平，或者只剩下一边 |

展开成具体问题：

| 编号 | 问题 | 例子 |
| --- | --- | --- |
| P1 | 实体碎片与误合并 | "急性心肌梗死 / 心梗 / AMI"成了三个节点；"二甲双胍"和"盐酸二甲双胍缓释片"却被合成一个 |
| P2 | 没有医学 schema，不锚定标准术语 | 同一个意思抽出"治疗 / 用于 / 可治"三种关系；实体挂不上 ICD-10、ATC 编码 |
| P3 | 断言丢失 | "ACEI 类药物妊娠期禁用"被抽成 (ACEI, 相关, 妊娠) |
| P4 | 冲突被抹平 | 见上表"有分歧" |
| P5 | 时效与版本 | 见上表"会过期" |
| P6 | 溯源只到文档级 | 说不清"eGFR < 30 禁用"出自哪份文件的哪一句；实体描述是 LLM 摘要过的二手知识 |
| P7 | 安全与越权 | 让 LLM 自己算儿童剂量；胸痛伴大汗的用户只得到"注意休息" |
| P8 | 不做条件匹配 | 能不能吃二甲双胍取决于 eGFR，向量检索不会追问这个条件 |
| P9 | 评测只看准确率 | 选择题答对了，长答案里却夹着一句致命错误 |

LightRAG 的实体按名字合并，同一实体的多条描述交给 LLM 摘要；关系是无向的，没有谓词类型；没有断言、有效期和冲突的概念；引用只到文档级。P1～P6 它基本覆盖不到，P7～P9 不在它的范围内。

## 3. 解决方案

### 3.1 知识表示：按风险分级 Claim 化

- **高风险知识抽成 Claim**，包括剂量、禁忌、相互作用、诊断阈值、控制目标、推荐意见。每条 Claim 由以下几部分组成：
  - 主体、谓词、客体；
  - 条件：人群、阈值、合并症、并用药；
  - 极性与推荐强度；
  - 有效期；
  - 原文出处：精确到句子和文档版本。
- **解释性文本**（机制、概述）保持文本块检索。这样成本可控，精力花在真正需要可验证的地方。
- **只处理知识文本**：指南、说明书、教材、政府文件、文献、医学问答，不处理病历、问诊对话这类患者文本。查询里的患者信息（如"我 eGFR 40"）由查询理解抽成条件。
- **断言与生俱来**：条件和极性在抽取时一次产出，不事后补。先建普通的实体关系图再回头补断言，等于全部重新抽一遍。

### 3.2 两条时间轴

| 时间轴 | 字段 | 含义 |
| --- | --- | --- |
| 现实有效期 | `valid_from` / `valid_to` | 这条知识在现实中何时有效 |
| 系统时间 | `recorded_at` / `retracted_at` | 系统何时得知、何时撤回 |

- 默认按"现在有效"的知识回答；也能回答"截至某年的标准是什么"；审计时可以还原任意时刻的知识状态。
- 文档有版本链，分三种情况：
  - **更正**（如 OCR 纠错）：覆盖原版本；
  - **修订**（新版说明书、新版指南）：保留旧版，并标记为被取代；
  - **不同机构的指南**：不是取代关系，而是并存。

### 3.3 冲突：分型、保留、按类型处理

业内的共识是冲突不消除，而是分型、保留、按规则排序、透明呈现。我们在 CONFLICTS 基准的 5 类基础上扩展成医学的 7 类：

| 类型 | 例子 | 处理 |
| --- | --- | --- |
| 互补 | 两份资料各说了不同的不良反应 | 合并呈现 |
| 条件不同（伪冲突） | 成人剂量与儿童剂量 | 补全条件后冲突消失，查询时按条件过滤 |
| 时效 | 说明书新旧版本 | 新版本优先；旧版本标为 deprecated，并写上 `valid_to` |
| 学术分歧 | 高血压诊断阈值 130/80 与 140/90 | 不裁决，两边都呈现，附发布机构和证据等级 |
| 证据等级不同 | 病例报告与 RCT 结论相反 | 按证据等级排序，低等级的作为补充 |
| 错误信息 | 低可信来源的说法 | 降权，进审核队列 |
| 抽取错误 | 系统自己漏抽条件造成的假冲突 | 回到原文复核，修正 Claim |

冲突在**入库时**检测并存下来（冲突集），不在每次查询时临时交给 LLM 判断。有研究发现，仅仅调换两篇文档的顺序，就会改变 11%～25% 的判断。

### 3.4 概念：规范化 + 可回滚的合并

- **锚定标准术语**：药物对应医保药品编码 / ATC，疾病对应 ICD-10，检验对应 LOINC。允许暂时锚定不了的概念存在，但要标出来。
- **粒度不同的不合并**，而是用关系连起来：成分—制剂—品牌、药物—类别、疾病—亚型。
- **合并可回滚**：每次合并都记成治理事件。查询时先只读地把候选碎片一起查上，回答完成后由后台判定是否真的合并。这就是查询驱动的治理，在开源库阶段完善。

### 3.5 回答：先对齐条件，再作答

- **双通道检索**：Claim 和文本块同时检索，并沿概念层级扩展。例如"ACEI 类妊娠禁用"也适用于依那普利。
- **条件匹配**：用户条件和 Claim 条件做结构化比较，结果分为满足、不满足、缺失三种；缺关键条件时返回追问。
- **逐句引用和核查**：每句标注引用，回答之后逐句核查。Claim 库没覆盖的部分用文本块作答，并标注"未结构化证据"。
- **回答路径只读**：查询不写知识库。查询中发现的碎片、未覆盖的文本、可疑的冲突，统统投进后台队列。

### 3.6 存储：关系库为唯一真相源

- **逻辑上**是超关系知识图谱：陈述 + 限定信息，与 Wikidata 的"陈述 + 限定词"同类。**物理上**存在关系库（PostgreSQL / SQLite）里。
- **向量索引**（Milvus / Milvus Lite）负责"找到"：文本块、Claim 的文本化表述、概念别名。
- **图数据库**（Neo4j / FalkorDBLite）**从第一阶段就上**。它是由治理事件驱动的投影，承担四件事：概念层级扩展；多跳查询（多药合用的相互作用、合并症）；解释路径；审核时的可视化。
- 向量和图都可以从关系库重建。

原则是"**向量负责找到，结构负责判断**"。医学里最致命的三类信息——否定、阈值、人群——恰恰是向量最不擅长的：在 NevIR 上，除了交叉编码器略高于随机，其他检索模型都不如随机。

Claim 在入库时离线构建，查询时只查不建。StructRAG、LazyGraphRAG 选择在查询时构建结构，但在医疗场景有四个硬伤：不可复现、冲突只能临时判断、没有审核机会、延迟高。

### 3.7 守护：core 给信号，上层定策略

- **core 提供**：
  - 确定性工具：剂量与肾功能调整、相互作用核对、禁忌核对。它们查询结构化的 Claim，不让 LLM 计算；
  - 逐句核查；
  - 风险信号：缺失条件、引用了过时知识、属于高风险内容；
  - 审计记录。
- **应用层负责**：越权识别（诊断、处方类请求）、急症红旗、PHI 脱敏、风险分级（直接返回 / 附提示 / 拦截或转人工），按受众配置。
- **合规**：《互联网诊疗监管细则（试行）》规定，人工智能软件不得冒用、替代医师本人提供诊疗服务；面向患者时不给诊断和处方。

### 3.8 评测：时间切片

- **流程**：文档按发布时间顺序分批入库，在每个时间点提问，以"当时有效"的答案为标准。这能直接暴露"增量入库时新旧描述被摘要到一起"的问题。
- **同时考察**：
  - 条件类：是否追问、是否按条件作答；
  - 分歧类：是否呈现双方；
  - 错误信息类：是否排除；
  - claim 级忠实度与安全关键错误率。
- **对比**：
  - 基线：不检索、文本块混合检索、LightRAG；
  - 消融：去掉条件、去掉有效期、去掉图扩展、去掉冲突集。

## 4. 与相关工作的区别

| 工作 | 做法 | 与本项目的差异 |
| --- | --- | --- |
| LightRAG、Microsoft GraphRAG | 入库时抽实体和关系，描述由 LLM 摘要 | 没有条件、有效期、冲突；溯源只到文档 |
| HippoRAG | 相似实体之间加同义边 | 只解决连通性，不处理粒度和断言 |
| Graphiti（Zep） | 双时态边，新事实使旧边失效 | 在时间维度上最接近，但面向通用的 Agent 记忆，是二元边，没有医学条件和证据等级 |
| StructRAG、LazyGraphRAG | 查询时临时把文档结构化 | 不可复现，冲突无法预先判定，没有审核环节 |
| Medical Graph RAG | 把实体链接到可信文献和 UMLS | 没有有效期和冲突处理；以英文为主 |
| KAG（OpenSPG） | schema 约束抽取、图与原文互索引、逻辑形式推理 | 不以时效和冲突为核心 |

## 5. 研制路线

### 5.1 阶段一：论文

范围：中文为主，纵向切片选**糖尿病、高血压、心血管一级预防**。先在窄领域把各层做薄、做通、测出效果，再往外扩，好让最大的风险——Claim 抽取质量撑不起整套设计——尽早暴露。

| 里程碑 | 内容 | 门槛 |
| --- | --- | --- |
| **M0 搬家**（已完成） | 包名改为 `medrag`；按新分层迁移；只用异步；OpenAI 兼容的模型层；版本化提示词；四个中间件未配置地址时降级；升级到 Python 3.12 | 硬门槛 `m0_parity.py verify` 数据层 9,999 行与查询编码 198 题 × 3 路均 0 差异；软门槛：检索指标在同一实现重跑的波动 + 2pp 以内（D17）；69 个测试通过 |
| **M1 基础层** | Document（版本与出处）/ Chunk / Evidence 类型；三类存储抽象（关系库、向量、图）及降级；治理事件与图投影机制（M1 先投影文档的版本链）；带版本语义的增量入库；文本块通道（稠密 + 稀疏融合）；门面的 `ainsert` / `aretrieve` / `adelete` | A 层回归（D17 原则）；同一份数据重复入库新增 0 行；关系库和图在两种后端上各测一遍 |
| **M2 切片语料** | 获取并解析指南、说明书、政府文件（PDF / HTML → 带章节的文本）；版本与出处元数据；清洗与 OCR 纠错（D13）；语料 manifest | 第 6 节 P0 数据齐全；解析结果抽检 |
| **M3 Claim 抽取** | 首版 schema（实体类型、谓词、条件）；抽取提示词；证据区间对齐；Claim 金标准（约 300 条） | 抽取的准确率和召回率达到在 dev 集上确定的目标（D37） |
| **M4 概念与图** | 概念规范化（词表 + 向量 + LLM）；导入医保药品编码、ICD-10、ATC；概念层级和 Claim 写入图投影；类别继承查询 | 概念链接准确率；图可以由事件重放重建 |
| **M5 时效与冲突** | 版本链与有效期推断；冲突检测与 7 类分型；rank | 冲突分型准确率（在标注集上评估） |
| **M6 按条件作答** | 查询理解（概念 + 条件）；双通道检索 + 图扩展；条件匹配与追问；逐句引用与核查；trace 与审计回放 | 在时间切片评测的 dev 集上明显优于基线 |
| **M7 论文评测** | 时间切片评测集（300～500 题）；基线与消融；报告与论文 | 拿到 test 集结果；RunManifest 可以复现 |

每个改动到存储或文本块检索的里程碑，都要先通过 A 层回归才能进入下一步。

### 5.2 阶段二：开源库

- **查询驱动的后台治理**：合并候选判定、未覆盖文本补抽 Claim、冲突复核、人工审核队列、按事件回滚。
- **英文支持**：DailyMed 说明书的历史版本、FDA 药品安全通告、ADA Standards of Care 的年度修订摘要。一个 workspace 只放一种语言（D16）。
- **工程完善**：数据下载与校验工具、命令行、文档与示例；规模化（全量教材、更多切片）；对标 GraphRAG-Bench medical。
- **应用层改造**：SimpleRAG / DialogueRAG / MedicalAgent 改为调用 core 的 `aquery`。
- **数据扩充**：Huatuo 百科全量、MIRAGE、CMB-Clin（用于多轮问诊评测）。

### 5.3 阶段三：产品

- **医生助手**：临床决策辅助，给出完整证据、版本和分歧。
- **患者助手**：健康咨询，回答保守、易读，做急症分诊。
- **守护层**：扩充确定性工具，加上风险分级、PHI 脱敏、急症红旗、审计与合规。
- **`software/`**：前后端适配新接口（D11）。

### 6.3 版权原则

- 期刊指南和商业说明书库只用于研究。评测集对外只发布标注、问题和出处，不分发原文。
- 政府文件可能适用《著作权法》第五条（行政性文件不受该法保护）。公开发布前需要确认（D34）。

## 7. 风险

| 风险 | 应对 |
| --- | --- |
