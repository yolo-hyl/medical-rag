# v2.0.0-rebuild 重构方案（第一阶段：数据、Schema、存储抽象）

> 目标：把 `MedicalRag` 从"一个 QA 型医疗 RAG 应用"重构成"像 LightRAG 那样分层抽象、专攻医疗领域的通用 RAG 库"。
> 本文是第一阶段的方案，范围只到 **数据接入、统一 Schema、存储抽象、增量入库、评测基线**，不包括图谱抽取、本体对齐和医疗安全层（后续阶段）。
> 写法约定：**【决策 Dn】** 标出的是需要你来定方向的地方，每条都给出了选项和我的建议；其余是我认为可以直接执行的部分。

---

## 0. 一页结论

1. 数据已经全部下载并检查过（第 1 节）。第一阶段用 **三层数据**：
   - **A 回归**：`qa_50000` + `new_qa_200`，按 `question_hash` 直接算 Hit@k，不需要 LLM 裁判；
   - **B 对标 LightRAG**：GraphRAG-Bench Medical，共 44 篇 NCCN 患者指南，2,062 道题，论文里有现成基线；
   - **C 中文主评测**：MedQA-Mainland 测试集 3,426 题 + 33 本中文教材（1,473 万字）。
2. 数据里有几处和之前预期不一样，会影响设计：
   - GraphRAG-Bench **其实有文档边界**；
   - 它的证据句几乎都不在原文里（8,175 条里只有 34 条能逐字找到），检索评测必须做语义匹配；
   - `new_qa_200` 的 `new_answer` 是 LLM 改写的，**带有原文没有的事实**；
   - 中文教材的 **OCR 错误很多**；
   - CMB 的测试集**没有答案**。
3. 重构按"先搬家、后改造"推进，分 M0–M4 五个里程碑。每个里程碑都以 A 层回归作为合并门槛。
4. 有 5 个决策会阻塞开工（D1–D5），见第 6 节。

## 1. 数据观察

### 1.1 A 层：`data/qa_50000.jsonl` + `data/eval/new_qa_200.jsonl`（仓库内，git lfs）

| 项 | 观察 |
| --- | --- |
| 规模 | 50,000 行，166 MB；字段 `question / answer / text / question_hash` |
| `text` | 所有行都满足 `text == question + "\n\n" + answer`，属于冗余字段，可以在入库时生成 |
| 长度 | answer 平均 541 字，中位数 629，最长 18,848；超过 2,000 字的有 347 条，超过 8,000 字的有 10 条，**需要切块** |
| 重复 | 有 57 个 `question_hash` 重复 |
| 来源 | **是 Huatuo-Encyclopedia-QA 的子集**：和百科集的 36 万行比对，问题重合 50,879 条 |
| 内容构成 | 按问题模式粗分：是什么 6,670、治疗 4,965、症状 4,196、诊断 3,137、用法用量 930、副作用 606、禁忌 495……约 40% 难以归类。混合了疾病百科、药品说明书和患者咨询三种文体 |
| 噪声 | 有非医疗内容（如"水松的栽培要点"）；有机翻残句（如"该反应在其他由引起的疾病中也可见"）；药品条目里有大量模板话术（"注意：同种药品可由于不同的包装规格……本文只供参考"） |
| 评测集 | **实际是 198 条，不是 200 条**；字段 `question / answer / question_hash / new_question / new_answer`。198 个 `question_hash` 全部能在语料里找到，可以直接算 Hit@k 和 MRR |
| 风险 | `new_answer` 是 qwen3:32b 改写的，会补充原文没有的事实。例如原答案只有"常见有肠坏死、肠套叠、肾功能衰竭等"，改写后多出了"约 30%-50% 患者会出现紫癜性肾炎"。拿它当参考答案，会把幻觉算成正确，见 **D7** |

## 2. 数据落地方式

- 新建 `data/benchmarks/`，放进 `.gitignore`。大文件**不进 git**，只提交下载脚本。
- `scripts/data/download.py <name>` 统一下载并做 sha256 校验，支持 `huatuo_qa`（git lfs）、`graphrag_bench`（仓库内已有）、`medqa`（gdown）、`mirage`、`medrag_textbooks`、`cmb`、`huatuo_encyclopedia`。本次已经验证当前环境能访问 HF、GitHub raw 和 Google Drive。

**核心接口草案**（M1 里定稿）：

```python
class Document(BaseModel):
    doc_id: str                 # 默认 md5(内容)，loader 也可以指定（如 question_hash、书名）
    content: str
    doc_type: Literal["qa", "textbook", "guideline", "drug_label", "literature", "other"]
    lang: Literal["zh", "en"]
    title: str = ""
    source: str = ""            # 数据集名或机构名
    metadata: dict = {}         # 由数据集决定：QA 的 question/answer，教材的书名和章节路径等

class Chunk(BaseModel):
    chunk_id: str               # f"{doc_id}-{序号}"
    doc_id: str
    content: str                # 送去 embedding 和 BM25 的文本
    summary: str = ""           # 可选的第二向量字段（QA 的 question、教材的章节标题）
    order: int
    section: str = ""           # 章节路径，如 "内科学/第二章/实验室检查"
    lang: str
    metadata: dict = {}

class QueryParam(BaseModel):    # 面向领域语义，不暴露 anns_field / expr
    mode: Literal["naive", "hybrid"] = "hybrid"   # 第一阶段只做这两种，local/global/mix 留给图谱阶段
    top_k: int = 10
    filters: dict = {}          # {"doc_type": "textbook", "source": "medqa_zh"}，由各存储实现翻译
    dense_weight: float | None = None
```

- `huatuo_qa` loader：`doc_id = question_hash`，一个 QA 对应一个 Document；超长答案按 qa_pair 策略切块，每块都带上问题。

- 引入 `DocStatusStorage`（pending / processing / processed / failed），支持断点续传。

| 编号 | 基线 | A | B | C |
| --- | --- | --- | --- | --- |
| B0 | 不检索 | — | ✓ | ✓ |
| B1 | 稠密 + BM25 加权融合（当前实现） | ✓ | ✓ | ✓ |

- **门槛**：
  - A 层不退化；
  - B 层的 B1 数字和论文里 "RAG w/o rerank" 在同一量级，如果差距超过 10pp，先排查流程；
  - C 层的 B1 / B3 要高于 B0，否则说明语料和题目对不上，要先查原因。

### M4 LightRAG 对标
- 用 `data/GraphRAG-Bench/Examples/run_lightrag.py` 在 B 层跑 LightRAG（hybrid / mix），生成模型和 embedding 与 B1 保持一致。

## 6. 需要你决策的地方

### 阻塞开工（M0 之前需要定）

**【D1】包名**
- (a) 保留 `MedicalRag`；
- (b) 改为 `medrag`（符合 PEP 8，和 Redis key 前缀 `medrag:` 一致）。

建议选 (b)。v2.0.0 本来就是不兼容升级，backend 和脚本反正都要改 import。不建议保留兼容层，那样会让新旧两套路径长期并存。

**【D2】LangChain 的边界**
- (a) 全栈继续使用 LangChain，迁移成本最低；
- (b) 核心层（storage / retrieval / ingest / medrag.py）不依赖 LangChain，LLM 和 Embedding 以 `async` 函数注入（和 LightRAG 一样），LangChain 和 LangGraph 只留在 `apps/`。

建议选 (b)，但分步做：M0 先把 LangChain 客户端包在 `LLMFunc / EmbeddingFunc` 协议后面，M3 再把核心层里的 LangChain import 清干净。这一条决定了这个库能不能被 LlamaIndex 或者别人自己写的 Agent 直接使用。

**【D3】稀疏检索策略**
- (a) 继续自己管理词表（pkuseg medicine 分词，医学术语切得更好）。缺点是 IDF 和 avgdl 在建词表时就冻结了，增量入库之后要定期重建词表；英文也需要另外接一个分词器。
